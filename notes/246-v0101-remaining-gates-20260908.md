## 3. Why initial packed-P graphs miss

`bindings/` balanced: initial P graph inputs use shared zero deepstack storage. Actual serving has
distinct per-layer deepstack bindings, row-dependent metadata addresses, and varying packed total-token
shapes. Physical KV backing is unchanged. Both address and shape mismatches are legitimate graph-key
differences; removing address checks would replay stale bindings.

`graph-bindings.json` retains 163 parsed snapshots. Initial captured shapes B2/total128 and B2/total168
do not represent all serving shapes (e.g. B5/total324). This identifies a concrete source of misses, not
proof that every miss has one cause.

Actual generic HTTP calibration capture safely populates graphs using runtime bindings. Existing
P32/D64 cache caps and exact binding identity remain. Serving capture is disabled at calibration end
unless separately requested by ONLINE_GRAPH_CAPTURE. Busy epoch changes are rejected before toggling.

First balanced capture screen: P serving hits11/misses119 (8.46%); D378/87 (81.29%).
Mixed: P0/38, D40/24. More D replay does not imply packed-P coverage solved.
Calibration cost-key counts/probe trajectories also change; this is a complete graph configuration A/B,

## 6. Same-prefix numerical result

Ordinary diagnostic multi-image3 runs, request2,32 steps: identical logits and token IDs despite different
row positions/batch membership. Pair12 and pair13 max absolute error0. This does not invalidate previous
nondeterminism: timing/instrumentation can move execution onto a different trajectory.

Canonical adapter diagnostic3 runs reproduced the issue. Pair001/002:

- Step0 already has same generated prefix but logits max abs difference0.2734375.
- Through step13 greedy choices still agree.
- Step14 is the **first argmax divergence** on the same generated prefix.
- Left top2: [198,151643], margin0.234375.
- Right top2: [151643,198], margin0.046875.
- Full-vocabulary max abs error0.48046875, mean abs0.07685514.
- Later steps have different prefixes and are intentionally excluded from physical-error comparison.

Thus the selected-token difference is already present in the model logits, not introduced by the CPU
output vector or JSON formatting. The argmax kernel already resolves exact ties by lower index; adding
a tie-breaking patch would not fix this nonzero-margin reversal. EOS-ignore request contract continues
sampling after natural EOS, so this branch is especially sensitive; changing that contract to hide the
difference would invalidate prior comparisons.

The remaining localization is encoder payload -> prefill hidden/KV -> decode logits, with identical
image preprocessing output and phase batch signatures. A small winner margin explains sensitivity,
but does NOT prove the upstream cause is harmless FP16 rounding or rule out ownership defects.

## 8. Acceptance and remaining work

### Startup binding correction

Source inspection found a concrete capacity mismatch: `buildTensorMap` initializes deepstack inputs
to `SharedResources::zeroBuffer`, sized for non-prefill `maxBatch * hiddenSize * sizeof(half)`.
Here that is80 *2048 *2 =327680 bytes. Startup packed-P128 requires524288 bytes, and external
P1024 requires4194304 bytes. The smoke harness zeroed `prefillIO.deepstackEmbeds` but did not bind
those tensors before its startup enqueues. The dedicated buffers already have sufficient capacity.

Commit `79e8b12` binds those dedicated per-layer tensors immediately after constructing the prefill
map; subsequent memset operations and external warmup use the same storage. No KV/page-pool change
and no increased buffer allocation. Serving's existing preprocessor already binds actual deepstack
buffers, so this patch is to the initial smoke/warmup path, not a demonstrated fix for serving logits.
This also invalidates treating the old startup graph-binding pattern as a desirable cache entry.
The full12 numbers above are **pre-correction screening**, not validation of the corrected binary.
Post-correction sanitizer (`vlm-memcheck-prefill-fix/`) did not finish startup in over5 minutes:
target CPU100%, GPU utilization0%, no further log progress. The specific test container was stopped
and the attempt is recorded as time-limited/incomplete, not a pass. `vlm-memcheck.log` belongs to this
last attempt; the prior serving-only failure log is copied to `vlm-memcheck-serving-failure.log`.
Corrected binary SHA256: `de690c2964c2e79e3094cfab5670f6d34b0a110692123d6c9abf976b28920dec`.
The previous immediate OOB was not re-reported before stopping, but that is insufficient evidence
that all affected launches executed successfully. Full sanitizer completion remains a blocker.
