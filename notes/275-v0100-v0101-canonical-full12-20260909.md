# 275. v0.10.0 and v0.10.1 canonical full12 comparison

## Conclusion

The v0.10.1 forward port has recovered the v0.10.0 execution frontier, but it
has not reproduced every old policy optimum.

- At fixed policy, v0.10.1 trails v0.10.0 by only **0.44% for V0** and **0.39%
  for V2** in 12-workload geometric-mean token throughput. V1 trails by 1.43%.
- Relative to each release's V0, v0.10.0 V1 gains 2.04%, while v0.10.1 V2
  gains 1.20%. Current V2 is 1.26% below the old V1 champion.
- Current V1 and V2 beat the unchanged frozen vLLM reference in throughput on
  all 12 workloads, by 11.52% and 11.71% geometric mean respectively.
- Current V2 beats frozen vLLM in E2E mean and p95 on all 12 workloads, but it
  does not win every TTFT or TPOT cell.
- The retained allocation before inference is 9,399 MiB on v0.10.1 versus
  9,581 MiB on v0.10.0. Both use the same 3,584 MiB FP16 KV pool. The old
  runtime encountered two vision-heavy allocation failures during 74 total
  attempts; the new runtime completed all 72 attempts.
- Greedy output is deterministic within every release/policy/workload cell.
  Cross-release exact hashes differ on decode-heavy, long-prefill, and bimodal,
  so the exact cross-engine identity gate is not yet fully closed.

The result is therefore **near release parity with better memory robustness**,
not universal policy dominance. The remaining work is paired action and
numerical-path diagnosis, not workload-specific tuning.

## Memory and reliability

| Runtime | ready allocation | nominal 10 GiB headroom | successful cells | failed attempts |
|---|---:|---:|---:|---:|
| v0.10.0 | 9,581 MiB | 659 MiB | 72/72 | 2 |
| v0.10.1 | 9,399 MiB | 841 MiB | 72/72 | 0 |

The two old-runtime failures occurred during the second vision-heavy attempt
for V1 and V2. Both reported `cudaMalloc(&data, memoryCapacity): out of
memory` after the 575 MiB vision workspace allocation. Fresh isolated retries
completed, yielding the required three successful samples for each cell.

This is 75% attempt success for those two old vision-heavy policy cells versus
9/9 successful v0.10.1 vision-heavy measurements. The 182 MiB lower retained
allocation is large enough to be operationally meaningful near the 10 GiB
limit. It is not a KV-cache reduction: page count, page size, KV precision,
active slots, and engine are identical. Exact allocator attribution still
requires a CUDA allocation ledger.

## Output identity

- All 72 aggregate cells are internally token deterministic across their three
  successful repetitions.
- Trace hashes and generated token counts match across releases.
- Cross-release exact token hashes match on 9/12 workloads.
- Mismatches occur on decode-heavy, long-prefill, and bimodal.
- Within either release, V0/V1/V2 hashes are identical on each of those
  workloads. Therefore the mismatch follows the release/runtime numerical
  path, not the selected policy or KV ownership mode.

Request-level old/new exact-sequence agreement is:

| Workload | exact requests | positional token agreement | first divergence |
|---|---:|---:|---:|
| decode-heavy | 192/288 (66.67%) | 82.56% | median 158; range 99--251 |
| long-prefill | 240/288 (83.33%) | 88.17% | median 44.5; range 25--64 |
| bimodal | 264/288 (91.67%) | 95.87% | token 212 for every divergence |

This pattern is consistent with a release-specific numerical path difference,
but the experiment does not identify whether the source is a plugin kernel,
tactic, binding shape, or another runtime operation. The production exact
cross-release greedy gate remains failed until logits and the first divergent
decode step are compared directly.

## Architectural interpretation

1. **The execution substrate is recovered.** Current V0 and V2 are within
   0.5% of the old equivalents across all 12 workloads. The previously observed
   large v0.10.1 regression was not an unavoidable KV or release limitation.
2. **The KV pool is not the performance differentiator.** Both releases use
   the same indexed-paged allocation and capacity contract. Memory improves
   without shrinking KV, while workload-specific throughput deltas change
   sign.
3. **V1 and V2 answer different questions.** V1 is the immediate learned-action
   control; V2 adds deterministic transition reasoning. V2 recovers aggregate
   current performance and multi-image behavior, but V1 still wins several
   workloads. Keeping both is required for causal evaluation.
4. **No workload label or workload-specific exception is needed.** Every run
   starts from the same generic calibration and learns only from continuous
   E/P/D state, measured cost, uncertainty, and deterministic transitions.
5. **Policy selection is not yet universally optimal.** The per-workload
   oracle is 1.04% above current V2. Closing that gap should come from better
   state/action realization evidence, not a table mapping workload names to
   policies.
6. **vLLM competitiveness and release parity are separate claims.** Current V2
   beats the frozen vLLM contract broadly, while still trailing the old V1
   champion slightly. Both facts are true.

## Next gates

1. Run paired telemetry for old/new V1 and V2 on bimodal, vision-heavy,
   poisson, text-heavy, mixed, multi-image, and late-vision. Compare action and
   membership hashes, requested/actual skew, completion order, WAIT placement,
   cohort formation, and host submission gaps.
2. Reproduce the first cross-release token divergence with identical row order,
   KV ownership, and bindings, then compare logits before greedy selection.
3. Add an allocation ledger around engine contexts, workspaces, KV pages,
   vision slabs, and graph-private buffers to attribute the 182 MiB reduction.
4. Promote a policy change only if it improves the 12-workload geometric mean,
   preserves workload-level latency gates, and does not introduce a new exact
   identity or OOM failure.
5. Rerun fresh vLLM only when the shared serving contract changes or for the
   final publication-quality repetition and confidence interval.
