# Gemma 4 E2B AWQ v0.10.1 phase-serving port

## Outcome

`Chunity/gemma-4-E2B-it-AWQ-4bit` was validated through the complete
checkpoint → ONNX export → TensorRT build → inference path on the RTX 3080. The standard VLM runtime and the
independent E/P/D phase runtime both execute the same text engine and vision engine successfully.

The port exposed two model-capability gaps in phase serving and fixed both:

1. Gemma 4's 4.7 GB per-layer embedding (PLE) table was consumed by model loading but was not transferred into the
   phase runtime.
2. An external-prefill TensorRT context was created only for packed-prefill engines, even though a non-packed VLM
   still classifies the post-encoder prompt as external prefill.

The resulting implementation shares one immutable PLE table between phase contexts and allocates only phase-local
gather outputs. Text prefill, external vision prefill, and decode have distinct TensorRT execution contexts. The text
and external-prefill contexts intentionally share the prefill workspace and therefore remain serialized with each
other; decode retains its independent context and workspace. The vision encoder owns a third independent engine
context and workspace.

## Export and build capability findings

Gemma 4 E2B uses attention head dimensions 256 and 512. The current packed-prefill v1 runtime accepts only head
dimension 128, so this model must use dense non-packed prefill until the d256/d512 packed kernels are implemented.
This restriction is independent of AWQ and PLE.

The default INT4 GEMM plugin v2 engine built successfully but failed during the first prefill execution on SM86 with
a TensorRT plugin execution error. Re-exporting the same decoder with `--int4-gemm-plugin-version 1` produced a valid
engine. The tested RTX 3080 contract is therefore:

```text
prefill layout       dense, non-packed
INT4 GEMM plugin     v1
max batch            1
max prefill batch    1
max decode batch     1
max input            1024
max KV capacity      2048
KV pool pages        16
KV dtype             FP16
```

All thinker, visual, and audio ONNX files pass `onnx.checker`. Only thinker and visual engines were built because
the current experiment is image/text VLM serving.

## Phase-local PLE design

The table is immutable and shared; the outputs are mutable and phase-local.

```text
                         PLE table
                [262144, 35 * 256] FP16
                       4,697,620,480 B
                              │
                    shared ownership
                    ┌─────────┴─────────┐
                    │                   │
              Prefill gather       Decode gather
              [35,1,1024,256]      [35,1,1,256]
                18,350,080 B           17,920 B
                    │                   │
          prefill TensorMap       decode TensorMap
                    │                   │
          prefill/external TRT      decode TRT
               contexts              context
```

This avoids duplicating the dominant PLE allocation. A unit test pins both invariants: the two preprocessors hold the
same table object, while every per-layer output binding points into a different phase-local workspace.

The runtime stages token IDs and runs the PLE gather on the same explicit stream as the consuming TensorRT enqueue.
No default stream or device-wide synchronization was added. This preserves the existing cross-stream correctness
contract while allowing P and D PLE generation to proceed independently.

## TensorRT and CUDA context topology

```text
one CUDA context
├── E stream → vision TensorRT context + 270.0 MiB workspace
├── P stream → text-prefill TensorRT context
│              ├── text prefill profile
│              └── shared 175.1 MiB workspace
├── P stream → external-prefill TensorRT context
│              └── same prefill workspace; serialized with text P
├── D stream → decode TensorRT context + 4.1 MiB workspace
└── C stream → vision payload copies
```

At initialization the GPU still had 1,500,971,008 free bytes before allocating the two small PLE output workspaces.
The standard single-context VLM path peaked at 8,558 MiB. A higher-batch phase engine should therefore be grown
incrementally rather than immediately targeting the earlier Cosmos batch limits.

### VLM legacy-versus-phase output identity

Both requests produced byte-identical output text across the legacy and phase runtimes.

| Request | Prompt tokens | Phase TTFT | Phase TPOT | Phase E2E | Result |
|---|---:|---:|---:|---:|---|
| One image | 502 | 159.705 ms | 7.439 ms | 390.299 ms | Correctly describes the person, dog, and sunset scene |
| Two images | 998 | 148.630 ms | 7.085 ms | 304.507 ms | Incorrectly asks the user to provide the images |

The two-image semantic failure is also exactly reproduced by the legacy path. It is therefore not caused by the new
PLE sharing or phase rebatching. Multi-image placement remains a separate pre-existing correctness issue.

The phase run reported 64.814 generated token/s and 848.587 ms wall time; the legacy smoke reported 91.1 generated
token/s and 603.57 ms. These are not promotion-quality performance numbers: the engine permits only one stable
request slot, the run has only two requests, and the phase CLI path includes phase-specific setup and admission
effects. They establish functionality and output parity, not scheduler speedup.

## Next experiments

1. Fix multi-image embedding placement using legacy/phase exact identity as the regression baseline.
2. Build the smallest useful asymmetric engine, initially P1–2/D4 with four stable KV slots. Retain this BS1 engine
   until the replacement passes output and memory gates.
3. Run controlled text-only and VLM arrival traces to determine whether the no-SLO V3 policy transfers without
   changing its workload-independent parameters.
4. Collect E/P/D/Copy activity masks and isolated kernel-group costs for Gemma. The d256/d512, dense-prefill costs
   should differ materially from the Cosmos calibration and are the intended input to online adaptation.
5. Compare V0/V1/V2/V3 only after the same higher-batch engine can form alternate actions. The current BS1 engine
   cannot evaluate batching or overlap policy quality.
6. Decide whether d256/d512 packed prefill is worth implementing. Until then, treat lack of chunked prefill as an
   engine capability constraint rather than a scheduler heuristic.
